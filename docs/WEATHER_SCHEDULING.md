# Weather scheduling

Weather is refreshed by an external uptime monitor. Configure a `HEAD` request to `https://<production-domain>/api/internal/weather/refresh` every 15 minutes with a timeout of at least 30 seconds. Send `Authorization: Bearer <token>`. If the monitor cannot send a custom header, use `?token=<token>` in the URL instead. Use exactly one form. Choose the canonical HTTPS domain directly so there is no redirect. Verify the monitor really sends `HEAD` and its credential; a generic 200 from a CDN or deployment protection page does not prove the Function ran.

Generate a random 32-byte token when activating the deployment. Store its SHA-256 hexadecimal digest in `BMO_WEATHER_TRIGGER_TOKEN_SHA256` on the server. Store the raw token only in the monitor configuration. The endpoint compares the digest in constant time and rejects missing, repeated, conflicting, or invalid credentials before touching the database. Rotate both monitor token and server digest in one maintenance window. Query tokens may appear in platform access logs; prefer the header.

The endpoint handles `HEAD` and `GET` with the same due gate and job. `HEAD` has no body. `GET` gives safe diagnostics for manual inspection. `200` with `not_due` or `busy` means the request was handled, not that weather is fresh. `503` means configuration, provider, database, or delivery failed. All responses disable caching. The Function has a 30-second maximum duration and gives the refresh and retained delivery a 25-second budget. A durable 900-second gate between provider attempts survives retries, cold starts, and multiple monitor regions. There is no Vercel weather cron.

Open-Meteo supplies current weather and geocoding data. The dashboard attributes both. Weather source time determines the 60-minute validity period; late monitor runs do not extend it. A failed provider request preserves the last observation. ESP32 devices receive retained weather only during their next wake network session; the server scheduler never wakes them.

Before activation verify remote Turso persistence, outbound HTTPS to Open-Meteo, broker TLS and ACL for `bmo/v1/devices/<deviceId>/weather`, retained persistence, updated firmware, and deployment protection access for the monitor. Keep `BMO_WEATHER_ENABLED=false` and the allowlist empty on previews. Run a production smoke test with the actual monitor and broker; local fixture tests do not establish those services' behavior.
